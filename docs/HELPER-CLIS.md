# Helper CLIs: detailed behaviour

The single place where every command, flag, field and error code of each skill's Python CLI is listed (the authoritative sources remain each skill's `USAGE.md`, `references/` and tests). `CLAUDE.md` names only what each script owns and changes only on structural events; every plan that changes a CLI updates this file instead.

## Commits

**Commits.** Only `plan-executor` commits on the user's branch, and only through `executor_tool.py commit-run`: in a chain after the audit, by hand with `/plan-executor <plan> commit` (a manual run with audit fixes lists them and waits for an explicit "yes"). It commits the run's files and the audit's fix files with the repository hooks; never push, `--amend`, `--force` or `--no-verify`. Per-unit snapshots stay hidden refs. `plan-resolver` stays git-read-only (no `add/commit/reset/checkout/clean/stash` in any phase); its gate only names the commit command. Without git, `run-diff --markdown` and `commit-run` fail with `no-git` and the `diffs` and `commit` stages are `skipped`.

## Per-skill CLIs

- `plan-executor/scripts/executor_tool.py`: argparse subcommands registered through `_register(...)` into `COMMANDS`, with a JSON result printed by `main`. It owns the execution ledger (`state.json`, schema in `assets/ledger.schema.json`). The ledger must be changed only through this tool. The agent loop uses `ledger-init`, `unit-begin` (next unit + strategy + that unit's text and files, marks it running) and `unit-finish` (snapshot + done, or failed + retry/stop decision). Whole plans: only `Task`/`Задача` headings become units when present, headings in code fences are ignored, units are strictly sequential, `**Tier:**` sets the weight. Roadmaps: the `### Task N:` headings of each part are units `task-<id>` (field `part`), each part closed by a checkpoint `part-<id>-done` over its completion criteria and handoff; a part without task headings stays one unit `<id>` (`part-without-tasks`); the drift fingerprint stays over the roadmap and the part files, so older ledgers resume. Snapshots are hidden refs `refs/plan-executor/<run>/<unit>` built with a temporary index and `commit-tree` (no branch commits). The ledger (v2) stores the plan SHA-256 for `plan-drift` detection. Errors are JSON with exit 2 (input) or 1 (contract). `ledger-init auto` puts the ledger in `<repo parent>/.exec/<repo>-<plan>/`, and `ledger-init` refuses an `exec_dir` inside the OS temp dir with exit 2 `exec-dir-ephemeral` unless `--allow-temp` is given (or the working tree itself lies there); `unit-begin` reports `external` lines (units that need confirmation), task weights are lowered for checkpoint/docs/test-only tasks, `unit-finish --note` records agreed deviations, `unit-begin`'s `strategy` carries `delegable` (light, main, not a checkpoint, no `External`), `ledger-init --light M` stores `settings.light` (the launch's model of delegated green units; `light-invalid`, exit 2, for an empty name), `unit-finish --delegated M` records `units[].delegated` and `delegated` in the journal's `unit-finish` event (`delegated-invalid`, exit 2), `run-diff` shows what the run changed, and `run-diff <exec_dir> --markdown [FILE] [--include-fixes JOURNAL]` writes it as the `<X>-diffs.md` report (a file table with status and `+`/`−` lines, then one `diff` block per file with an adaptive fence, cut at 400 lines; pipeline artifacts excluded — `BACKLOG.md`, the run's journal and the chain-file names in the run's plan folder only (`_is_run_artifact`; the same name elsewhere is the run's work) — and listed in a "Not included (pipeline artifacts)" section; `--include-fixes` adds the audit's `fix_files` against the working tree, and fix files git ignores are returned as `ignored` and listed in a "Not included (ignored by git)" section). Outside git it fails with `no-git` (exit 1), distinct from `run-diff-unavailable` (no finished unit). `ledger-init` also stores the chain settings (`settings`, and `settings_source` with the SHA-256 of the spec or plan header they came from); on resume it clears `consents` and stops with `settings-drift` (`changed_keys`) when that file changed, unless `--accept-drift`. `unit-begin` returns `external` as `{env, access, kind, consent, confirmed, source}` objects and first compares the working tree with the ledger's `expected_tree`: a difference gives `reason: foreign-changes` with `foreign_changes: [{path, status}]` (skipped for an in-progress unit, `null` outside git, `BACKLOG.md` ignored). `consent <exec_dir> <env> read|write` records a run-scope consent (refused for prod writes, for `deny` and for unknown environments); `accept-changes [--note]` takes the current tree as expected and, when there were foreign changes, logs a `foreign_events` entry (`event: null` otherwise); `checkpoint-restore --paths P …` restores only the listed files (paths relative to the repository root, like `foreign_changes`; nothing left after excluding `BACKLOG.md` and the chain files → `paths-empty`, exit 2; a file equal to the snapshot is `unchanged`), and `--exec-dir D` moves `expected_tree` (every restore the executor makes itself passes it). The pipeline's own files (`BACKLOG.md` at the root; the run's own journal and its lock wherever they lie; by name in the run's plan folder, in any folder without a ledger, `*-chain.json` and its lock, specs, plans, parts, roadmaps, completion, review and report files, `*-diffs.md`, `*-followups.json`) are never foreign changes and never restored, and the chain journal is in no snapshot; none of them (except a `*-chain.json` other than the run's journal) makes the working tree dirty. `ledger-path <plan> --workdir <repo>` returns the `auto` ledger directory, whether it exists and `matched` (`plan` or `roadmap`: for a plan with a `<X>-roadmap.md` beside it the roadmap's run is found too; both runs → `ledger-ambiguous`, exit 2), read-only. `ledger-init` also stores `baseline_head` (HEAD at the first init, `""` for an unborn HEAD) and `journal` (`{path, plan}` of the chain journal, or `null`) and moves the journal's `execution` stage to `running` with the artifact `exec_dir` (relative to the journal's directory); `unit-begin` and `unit-finish` write the unit events into the journal themselves, `unit-finish` (and `ledger-init`) the artifacts `units_done`/`units_total`, `unit-begin` the end of `execution` (`done` or `failed`), and a failed journal call only adds `journal_error` to the output. `commit-run <exec_dir> --message-file F [--journal J]` commits the run's files plus the audit's `fix_files` minus pipeline artifacts and files already equal to `HEAD`, checking in this order: `no-git`, `baseline-head-unknown` (an old ledger without `baseline_head`), `index-not-empty`, `snapshots-missing` (the run's snapshots pruned and garbage-collected; only the expected tree missing → the error names `accept-changes`), `run-incomplete` (a unit still `running`, field `units`), `failed-attempt` (a `failed` unit not rolled back: commit-set files that differ from the last done snapshot and are not audit fixes, field `files`), `head-moved` (`baseline_head` is no ancestor of `HEAD`), `mixed-files` (the file had uncommitted work at `baseline_head` and the run changed it), `foreign-changes`, then an empty set → `empty: true`, then `bad-subject` (the subject must match `<type>(<scope>): …` within 72 characters, exit 2). It commits with the repository hooks (a failing hook → `commit-failed`, index reset to its previous state), returns `excluded`, `excluded_outside_chain` (a `*-chain.json` in the plan's folder other than the run's journal) and `incomplete` (`failed`/`pending` units, a warning), `backlog` (`section`, `appended`, `exists`; only when there are deviations: `plan_deviations` takes the plan header's `**Deviations from spec:**` items and the units' notes except `subagent-unavailable` and the `External:` confirmations, appended once as `amend spec <spec>: <gist>` to the goal's `BACKLOG.md` section through `brainstorm_tool.backlog_append`) and `warnings` (`backlog-unavailable`, `backlog-write-failed`; never a refusal), records the commit in the journal, and never uses `--no-verify`, `--amend`, `--force` or push. `detect-input`, `parse-roadmap` and so `ledger-init` refuse a goal roadmap of `plan-brainstorming` (`> Goal:` among the first ten lines; `_GOAL_ROADMAP_RE`, a copy of `brainstorm_tool.GOAL_ROADMAP_RE`) with exit 2 `not-a-split-roadmap: this is a goal roadmap; run /plan-chain-runner <file>`, and a plan `<X>.md` next to such an `<X>-roadmap.md` stays `whole`. `_CHAIN_FILE_RE` treats every `*-roadmap.md` in the plan folder as a chain file (`chain_tool._CHAIN_FILE_FALLBACK_RE` is an equal copy). `_CHAIN_FILE_RE` also matches the skills' temporary files (spec 1 of plan-refactoring-05; the one list of them is the comment above it; four equal copies, `plan-writing/tests` `ChainFileReContractTest`), and `BACKLOG_TEMP_RE` (`.BACKLOG.md.<random>.tmp`; copies in `next_review_index.py` and `resolver_tool.py`) is free at the root like `BACKLOG.md`. `delegate-check <repo> --snapshot-out F` writes the snapshot of a delegated unit before its subagent (version 3, spec 1 of plan-refactoring-05: `brainstorm_tool.worktree_snapshot` of the root after `realpath` with `origin: git`, `head`, `plan_dir` — the plan's folder of the ledger in `F`'s folder — and the `git status` entries, `F` itself left out; exit 1 `snapshot-unavailable` without plan-brainstorming alongside, exit 1 `snapshot-failed` when git fails), and `delegate-check <repo> --snapshot F --reply R` (`F` and `R` are left out of the comparison when they lie in the repository, an `exec_dir` inside it being allowed while git ignores it) reads the `Written files:` block that ends the subagent's saved reply `R` (spec 2 of plan-refactoring-04: paths relative inside the root and absolute outside it, or `Written files: none`; `_written_files`) and returns `verdict` (`pass`/`fail`), `reply_error` (`written-list-missing` when the block is missing, not the last one, empty or followed by paths after `none`), `outside` (named paths outside the root after `realpath`/`normcase`), `unreported` (changed, not named; unnamed pipeline files by name and ignored paths outside the plan's folder left out), `phantom` (named, not changed; never a path ignored outside the plan's folder), `head_moved` (`fail`), `changed` (without `ignored_changed`), `ignored_changed`, `origin` and `warnings`; exit 1 `no-git`, exit 2 `snapshot-invalid` (a version 1 or 2 snapshot included), `reply-unreadable`, `delegate-check-usage` (`--snapshot` without `--reply`, `--reply` with `--snapshot-out`) or an argument error (`--files` was removed). `checkpoint-prune <exec_dir>` also removes the `delegate-*.json` and `delegate-*-reply.md` files at the top of `<exec_dir>`, with git or without, and returns `{pruned, removed, warnings}` (`delegate-remove-failed: <name>`, exit 0). A delegable unit run in the main agent for want of a subagent tool is finished with `--note subagent-unavailable`. `ledger-init` refuses a whole plan that still carries plan-writing's writing marker with exit 1 `plan-incomplete`. `run-diff --markdown` without a value writes the report to `diffs_path` of the ledger's `plan_path` (`<X>-diffs.md` next to the master plan; a roadmap `<X>-impl-roadmap.md` names `<X>-impl.md`) and returns it as `markdown` (and `path`); another `FILE` is exit 2 `diffs-path-mismatch` (field `markdown`; after `no-git` and `run-diff-unavailable`), nothing written; FINALIZE and COMMIT write the same file. `extract_files` (spec 1 of plan-refactoring-04): of a `Files` action line (`Create`, `Modify`, `Test`, `Delete`, `Move` and the Russian ones) only its path is taken — the first backticked name or markdown link by position, the first two for `Move:` — and a name with `<` or `>` (a placeholder such as `<base>-diffs.md`) is no path; other lines of the block and the `## Inputs/Outputs` sections of parts give every name as before; `brainstorm_tool._plan_task_files` keeps the same rule (`plan-writing/tests` `FilesContractTest`, on a copy of plan 03).
- `plan-splitter/scripts/splitter_tool.py`: hand-rolled `argv` dispatch in `main`. Parts are named `<base>-a.md`, `<base>-b.md`, … (`part_id`, bijective base-26) with the roadmap at `<base>-roadmap.md`. It handles preflight, part and roadmap validation, and the verify baseline/record/status commands; `verify-record` turns plan-iterative-revision's batch JSON into the verify ledger. `gate <plan>` (and the pure `gate_verdict`) decides keep / split / borderline from `task_count`, `plan_bytes`, `modules` and `dependency_shape` of `brainstorm_tool.parse_plan_tasks` (thresholds 20 tasks / 100 KB / 40 tasks / 150 KB / 3 modules, flags to change them; exit 1 `no-tasks`); `split-write <plan> --parts <json>` checks the model's boundaries (`tasks-unassigned`, `tasks-duplicated`, `tasks-unknown`, `part-ids-not-sequential`, `unknown-dependency`, `dependency-cycle`, `group-conflict`, `dependency-order`, `missing-depends`; warnings `subtask-separated`, `lines-outside-tasks`) and only then writes the roadmap and parts from the templates, copying task texts byte for byte, so `**External:**`, `**Size:**` and `**Structural event:**` lines reach the parts, and comparing the task ids of `parts.json` normalized (`01` = `1`) (`exists` without `--force`); `validate-all` requires equal task coverage and checks `task_bodies` by `sha1` (`--skip-task-bodies` after a full-cycle verification). These three exit 2 without `plan-brainstorming`. `preflight <dir> <base>` exits 1 with `error: plan-incomplete: …` when the plan `<base>.md` in `<dir>` still carries plan-writing's writing marker. `gate` and `gate_verdict` also return `silent_verdict`, the decision without a confirmation channel: `verdict` for `keep` and `split`; for `borderline` `keep` within `split_tasks` and `split_bytes`, else `split`. Without a confirmation channel no table is shown: `parts.json` goes straight to `split-write`, and the `done` event carries the table as one artifact string `parts_table` (parts separated by ` | `, replaced on every write).
- `plan-resolver/scripts/resolver_tool.py`: argparse. It handles bootstrap, preflight, `fingerprint-workspace <root> <out> [--plan P] [--base B]` (writes `brainstorm_tool.worktree_snapshot` of the working tree plus `workspace`, the root it was given: with git the repository's top level, `HEAD`, the paths `git status` lists with their blob hashes and the ignored files of the plan's folder with SHA-256, so clean tracked files are never read; without git a walk ignoring by the root `.gitignore`; `--base` has no effect, warning `base-ignored`; exit 1 `snapshot-unavailable` without plan-brainstorming alongside, `snapshot-failed` when git fails; exit 2 `fingerprint-out-json-inside-workspace` when `<out>` lies inside the workspace) plus `assert-readonly <start> <current> <allowed> [<allowed> …] [--plan P]` (`brainstorm_tool.worktree_diff`: `violations` — a changed file git does not ignore or of the plan's folder, `HEAD` for a moved HEAD —, `ignored_changed` for ignored paths outside the plan's folder, information only, `head_moved`, `origin`; without `--plan` the warning `plan-unknown` and every changed ignored path a violation; the resolver writes only its report and `BACKLOG.md`; the audit's journal end records `origin` as the artifact `guard=<git|walk>`), report parsing and validation (`validate-report --root` also verifies evidence anchors against the workspace), the stuck-open gate inside `bootstrap`, `snapshot-diff` (`changed` without the ignored paths outside the plan's folder, which come as `ignored_changed` and never become `fix_files`; `added`/`removed`/`modified`; `origin`), the fix-loop commands (`discover`, `open-issues`, `protect`, `mark-fix`, `cycle-check`), and `task-census` (every plan task must be covered in the report). `validate-report --plan` lets only tasks without code files be closed by `evidence_probe`, and lists `verification: executor-reported` tasks as warnings. Incremental re-audit: `evidence-fingerprint <report> --snapshot <start> --plan <plan>` writes the report's `## Evidence fingerprint` section (the SHA-256, taken when the command runs, of every file named by stage anchors, issue evidence and the plan tasks' `Files` by `brainstorm_tool.parse_plan_tasks`, or `missing`; `excluded` is no longer written, and an older report's `excluded` or `missing` row makes its file unverified; never `BACKLOG.md` or a chain file of the plan's folder by `CHAIN_FILE_RE`, a copy of the executor's `_CHAIN_FILE_RE`, and `rescan-scope` ignores such rows of older reports; replaced whole, before the Fix Log; exit 2 `snapshot-root-mismatch`); `rescan-scope <plan> <last-report> --snapshot <start> [--ratio 0.5]` hashes the last report's evidence files again and returns `changed_files`, `missing_files`, `unverified_files`, `reaudit`, `carry`, `audit_tasks`, `titles`, `line_ranges`, `issues`, `plan_sha_changed`, `scope` (`incremental`, or `full` with `plan-changed`, `no-evidence-fingerprint` or `ratio` above `FULL_SCOPE_RATIO = 0.5`) and `reason`; `carry-forward <last-report> --scope <json> --header <json> --out <report>` writes the incremental draft (`audit_scope: incremental`, `audit_tasks`, carried lines byte for byte, `<!-- reaudit -->` stubs, issue blocks with `<!-- re-verify -->` on open ones; exit 2 `report-exists`, `inputs-inside-workspace`, `scope-mismatch`, `header-missing-fields`, `bad-input-json`, exit 1 `use-full-pass`). `validate-report` checks `audit_scope`/`audit_tasks` (missing: a warning, read as full), rejects leftover markers and malformed evidence rows and requires `audit_scope: full` for `-final`; `bootstrap --full` gives `pass_type: subsequent-full`; `cycle-check` answers `full-audit-required` for an open incremental report with everything closed, and the full pass after it never gives `stop-stalled`. `validate-report` also warns `verbose-closed-task: <id> has N detail lines` (a `✅` leaf with more than one detail line) and `too-many-anchors: <id> has N anchors` (more than two), never errors; `parse-report` gives every stage item `details`. The agent reads the plan through `plan_tool.py skeleton`/`task` of `plan-writing` on the first and full passes, and in full without it. Task ids are compared by `normalize_plan_task_id` (lower case, `01.02` → `1.2`); paths by `path_inside`/`ensure_inside` after `realpath` and `normcase` (a link to the workspace is inside, a link out of it is not), and a plan, report or snapshot that is not UTF-8 is a JSON error with exit 2 (`not-utf8: …`, `invalid fingerprint snapshot: …`).
- `plan-iterative-revision/scripts/next_review_index.py`: hand-rolled dispatch. `bootstrap` starts a run and returns `settings` (plan header, else the spec at `**Spec:**`; a roadmap goes through its Source link); `record` takes the agent's issues JSON and is the single authority for loop gates (clean/converged/drain/regression/unchanged/churn/stuck/limit over the current run's history). It also computes the fingerprints (SHA-1 of category + required fix, first 8 characters), then renders, writes and strictly validates the review or completion file. `guard-begin`/`guard-check` keep diff-guard snapshots in the OS temp dir: `brainstorm_tool.worktree_snapshot` of the git root with the `--plan` plan's folder (spec 1 of plan-refactoring-05: `HEAD`, `git status` with blob hashes, the plan folder's ignored files with size, mtime and SHA-256; `guard-begin` returns `files`, the number of entries; `snapshot-failed` is exit 1), or `git status` without plan-brainstorming alongside (`changed_count` as before, warning `snapshot-unavailable`); `guard-check` never counts `BACKLOG.md` or its temp file at the repository root as a violation (free files), returns `ignored_changed` (ignored paths outside the plan's folder: information, never written into the review), makes a moved `HEAD` the violation `HEAD`, and returns `free`: changed files with a pipeline name (`CHAIN_FILE_RE`, a copy of `executor_tool._CHAIN_FILE_RE` held equal by `plan-writing/tests` `ChainFileReContractTest`) that are not the plan's own (`own_plan_file`: the plan, its reviews, completion file, parts, roadmap and `<X>-diffs.md`; the plan of `--plan`), which are no violation; without `--plan` nothing is `free`. `record --free N` writes `**Concurrent pipeline files**: N (previous pass)` as the last header line of the review (exit 64 for a value that is not a non-negative integer). The low-level commands (`validate-review`, `flow-analyze`, `digest`, ...) remain; `plan-splitter` calls `validate-review`. Fixtures are in `.fixtures/`. `bootstrap` also returns `journal` (the chain journal path when the file exists, else `null`), and `record` returns `journal_event`: `{stage: "revision", status, artifacts: [review=…, completion=…, verdict=…]}` with `status: "done"` and `input` (the plan path) for `clean`, `converged`, `drain` and `audit-only`, `status: "stopped"` for `limit`, `user-stop`, `regression`, `unchanged`, `churn` and `stuck`, and `null` while the loop continues; the agent passes it to `journal-event`. Incremental re-audit: `record --scope full|incremental [--tasks <ids>]` writes `**Audit scope**`/`**Audit tasks**` and the `## Task digest` table (task id + 8-hex SHA-1 by `brainstorm_tool.parse_plan_tasks`, loaded by path; no table without it, for a plan without tasks or with repeated ids); `--scope incremental` is an input error (exit 64) on the first audit of a run, without `--tasks`, with a task id the plan does not have, or with `--mode audit-only`; an incremental audit without issues gets `action: full-audit-required` (nothing written, the same audit again in full), and a skipped contract whose tasks are all unchanged and none of them in `--tasks` is carried back with the warning `contracts-dropped` (a contract the audit had in scope and left out is closed); a contract that cannot be carried back is exit 64 `contracts-carry-failed: …`. Task ids of `--tasks`, of contracts and of the `## Task digest` table are compared by `normalize_task_id` (`01.02` → `1.2`). `digest` adds `task_digest` (`available`, `plan_sha_changed`, `changed`, `new`, `removed`, `unchanged`, `focus`, `dependents`, `tasks`, `line_ranges`, `changed_ratio`, `scope`: `none-changed` | `incremental` | `full`, `reason`, `warnings`; full above `FULL_SCOPE_RATIO = 0.5`) for the plan of the latest review's `**Audited plan**`, and `validate-review` warns `task-digest-malformed`. `record` warns `evidence-too-long` for an issue whose `evidence` (after duplicates are merged) is over 600 characters; the text is not cut. `bootstrap` reports `plan-incomplete: …` in `errors` (`valid: false`, exit 1) for a plan that still carries plan-writing's writing marker. Budget (spec 1 of plan-refactoring-04): `record` with `action: implement` returns `budget` `{plan_bytes, tasks, max_bytes, max_tasks, headroom_bytes, limit}` (`headroom_bytes` = 150 000 minus the plan file's size now; no headroom → `limit: off`, the warning `oversized-before-revision: N bytes > 150000` and the review line `**Budget**: off — oversized before revision (N bytes > 150000)`), `null` for other actions and, with the warning `budget-unavailable`, without plan-brainstorming; `record --deferred "N.k:budget,…"` writes `[N.k] deferred: budget` under `## Deferred from previous review` and carries an issue of the run's latest review the audit left out (exit 64 on the first audit, for an unknown id or another form). `guard-begin <root> <label> --plan PLAN` keeps the plan's path, bytes and task hashes in the snapshot (also without git, exit 3), and `guard-check` then adds `plan_bytes_before`, `plan_bytes_after`, `changed_tasks` and `over_budget` (the plan had room and is over 150 000 bytes now), also without git; without `--plan` both add `warnings: ["plan-unknown"]`. Code between passes: `record` writes `**Code changed tasks**` and, after the Task digest, the `## Code digest` table (per Files path of the tasks the first 12 hex of its SHA-256 or `missing`, `unreadable`, `dir`, `glob`, `outside`; root: the git top-level, else the current directory), and `digest`'s `task_digest` adds `code_changed`: the tasks whose files changed state, which with their dependents enter the scope and `changed_ratio` (an unchanged plan whose code changed is not `none-changed`); warnings `no-code-digest`, `code-root-cwd`.
- `plan-writing/scripts/plan_tool.py`: argparse. `plan-path` (`<X>-spec.md` → `<X>-impl.md`) and `plan-check` (plan format contract, including the `**Environments:**` header block with quoted user permissions and per-task `**External:**` lines: `**Spec:**`/`**Tier:**` header, task headings and unique ids, task core per tier, backticked file paths, no commit steps, no placeholders; `--root` checks Modify targets). Reference plan in `tests/fixtures/`. Tasks, their bodies and code line counts come from `brainstorm_tool.parse_plan_tasks` (a task ends at the next task heading or a heading of its level or higher; without `plan-brainstorming` the local `_local_plan_tasks` with the old rules and the warning `plan-brainstorming not installed alongside`); each entry of `tasks` has `line`, the heading's line number. `plan-check` reads the chain settings through `brainstorm_tool.resolve_settings` (plan header, else the spec at `**Spec:**`) and returns `settings`, `task_count`, `plan_bytes`, `lang`, `oversized`, `size_class` (`small` ≤ 15 tasks, `large` over the budget, else `medium`; `null` without tasks) and `budget` (`tasks`, `bytes`, `source`: `brainstorm_tool`, `default` or `flags`). Above the budget (`brainstorm_tool.SIZE_BUDGET`, 40 tasks or 150000 bytes; `--max-tasks`/`--max-bytes` override it, a value that is not a positive integer is exit 2) it warns `plan-oversized: N tasks, M bytes (budget …)`, never an error. ## Cross-skill coupling

**Cross-skill coupling.** `plan-writing` runs `../plan-brainstorming/scripts/brainstorm_tool.py spec-check` by relative path, so both skills must be installed side by side. `plan_tool.py`, `executor_tool.py`, `next_review_index.py`, `resolver_tool.py` and `splitter_tool.py` also load `../plan-brainstorming/scripts/brainstorm_tool.py` by path (`importlib`, no subprocess) for `resolve_settings` and the chain journal (`journal_path_for` gives the `journal` field of `plan-check` and `bootstrap`; `executor_tool.py` also calls `journal_create`, `journal_event`, `journal_unit`, `journal_add_commit` and `journal_load` from `ledger-init`, `unit-begin`, `unit-finish`, `commit-run` and `run-diff --include-fixes`); the splitter and resolver agents call its `settings` CLI, the executor and resolver agents call its `backlog-append`, and the agents of all six pipeline skills call its journal CLI (`journal-path`, `journal-event`, `journal-question`, `journal-answer`, `journal-finding`, `journal-export-findings`, `journal-show`), and the `plan-chain-runner` agent also calls its `spec-check` and `journal-reconcile`. Without it the settings come back empty with the warning `plan-brainstorming not installed alongside`, and the skills run without a journal. `chain_tool.py` loads it the same way, to read and write the journal (the `runner` section) and to read each spec's chain settings (`resolve_settings`), and cannot run the journal without it: `settings-save`, `run-init`, `run-session`, `run-next`, `run-eta` and `run-status` fail with exit 2 `plan-brainstorming not installed alongside`; `settings-load` and `model-pick` without `--journal` work alone (`model-pick --journal` fails the same way). `chain_tool.py` also loads `../plan-splitter/scripts/splitter_tool.py` by path for `gate_verdict` (the numeric gate of `split=auto`; missing or failing → the split stage runs with `gate-unavailable`), and the splitter's `gate`, `split-write` and `validate-all` need `brainstorm_tool.parse_plan_tasks` (exit 2 `plan-brainstorming not installed alongside` without it). The settings lines (`> Chain:`, `> Environment:`, `> Backlog:`, `**Chain:**`, `**Environments:**`, `**Backlog:**`) are parsed only there, and the task lines `**External:**` and `**Size:**` are carried into split parts verbatim. Output formats are also contracts between skills: splitter roadmap/part formats are parsed by `executor_tool.py parse-roadmap` and by `next_review_index.py parts` (batch mode); part ids are letters and the three parsers must agree, and plan task headings (`### Task N: <title>`) are parsed once, by `brainstorm_tool.parse_plan_tasks`, which `plan-check` always uses and the executor, the resolver's `task-census`, the splitter's count and `chain_tool.py run-stats` use for a plan with contract task headings and no malformed one (their own parsers stay for other plans and without `plan-brainstorming`); `plan_tool.py plan-check` enforces that format, and `plan-writing/tests` holds contract tests against both parsers. The chain journal (stage names, statuses, transitions, owners, artifact keys) is a contract between all six skills and `plan-chain-runner`, which schedules by it and owns its optional `runner` section; `plan-writing/tests/test_journal_contract.py` replays their event sequence for one plan against `journal-validate` and `journal-show`. `plan-chain-runner` launches the six skills by name with the arguments `run-next` returns (`/plan-writing <spec>`, `/plan-executor <plan or roadmap>`, `/plan-resolver <plan> fix|auto`, `/plan-executor <plan> commit`, …) and takes the roadmap from the `split` stage's artifacts, so a change of a skill's arguments or stage artifacts must be checked against `chain_tool.py` too. A format change in one skill must be checked against the parsers in the others. The goal roadmap `<goal>-roadmap.md` is a contract between `plan-brainstorming` (`roadmap-write`, `roadmap-check`, `roadmap-parse`) and `plan-chain-runner` (`/plan-chain-runner <goal>-roadmap.md`; `chain_tool.py` reads it in-process through `parse_goal_roadmap` for `run-init --roadmap`, `subset-check` and `run-status`); `executor_tool._GOAL_ROADMAP_RE` copies `brainstorm_tool.GOAL_ROADMAP_RE` and `chain_tool._CHAIN_FILE_FALLBACK_RE` copies `executor_tool._CHAIN_FILE_RE`, each pair checked by a contract test.
