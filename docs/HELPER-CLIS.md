# Helper CLIs: detailed behaviour

This is the detailed description of each skill's Python CLI that used to live in `CLAUDE.md`. The authoritative sources are each skill's `USAGE.md`, `references/` and tests; this file is a consolidated map. Keep it in sync when a command's behaviour changes.

## Commits

**Commits.** Only `plan-executor` commits on the user's branch, and only through `executor_tool.py commit-run`: in a chain after the audit, by hand with `/plan-executor <plan> commit` (a manual run with audit fixes lists them and waits for an explicit "yes"). It commits the run's files and the audit's fix files with the repository hooks; never push, `--amend`, `--force` or `--no-verify`. Per-unit snapshots stay hidden refs. `plan-resolver` stays git-read-only (no `add/commit/reset/checkout/clean/stash` in any phase); its gate only names the commit command. Without git, `run-diff --markdown` and `commit-run` fail with `no-git` and the `diffs` and `commit` stages are `skipped`.

## Per-skill CLIs

- `plan-executor/scripts/executor_tool.py`: argparse subcommands registered through `_register(...)` into `COMMANDS`, with a JSON result printed by `main`. It owns the execution ledger (`state.json`, schema in `assets/ledger.schema.json`). The ledger must be changed only through this tool. The agent loop uses `ledger-init`, `unit-begin` (next unit + strategy + that unit's text and files, marks it running) and `unit-finish` (snapshot + done, or failed + retry/stop decision). Whole plans: only `Task`/`Задача` headings become units when present, headings in code fences are ignored, units are strictly sequential, `**Tier:**` sets the weight. Roadmaps: the `### Task N:` headings of each part are units `task-<id>` (field `part`), each part closed by a checkpoint `part-<id>-done` over its completion criteria and handoff; a part without task headings stays one unit `<id>` (`part-without-tasks`); the drift fingerprint stays over the roadmap and the part files, so older ledgers resume. Snapshots are hidden refs `refs/plan-executor/<run>/<unit>` built with a temporary index and `commit-tree` (no branch commits). The ledger (v2) stores the plan SHA-256 for `plan-drift` detection. Errors are JSON with exit 2 (input) or 1 (contract). `ledger-init auto` puts the ledger in `<repo parent>/.exec/<repo>-<plan>/` and refuses temp dirs; `unit-begin` reports `external` lines (units that need confirmation), task weights are lowered for checkpoint/docs/test-only tasks, `unit-finish --note` records agreed deviations, `run-diff` shows what the run changed, and `run-diff <exec_dir> --markdown FILE [--include-fixes JOURNAL]` writes it as the `<base>-diffs.md` report (a file table with status and `+`/`−` lines, then one `diff` block per file with an adaptive fence, cut at 400 lines; pipeline artifacts and `BACKLOG.md` excluded and listed in a "Not included (pipeline artifacts)" section; `--include-fixes` adds the audit's `fix_files` against the working tree, and fix files git ignores are returned as `ignored` and listed in a "Not included (ignored by git)" section). Outside git it fails with `no-git` (exit 1), distinct from `run-diff-unavailable` (no finished unit). `ledger-init` also stores the chain settings (`settings`, and `settings_source` with the SHA-256 of the spec or plan header they came from); on resume it clears `consents` and stops with `settings-drift` (`changed_keys`) when that file changed, unless `--accept-drift`. `unit-begin` returns `external` as `{env, access, kind, consent, confirmed, source}` objects and first compares the working tree with the ledger's `expected_tree`: a difference gives `reason: foreign-changes` with `foreign_changes: [{path, status}]` (skipped for an in-progress unit, `null` outside git, `BACKLOG.md` ignored). `consent <exec_dir> <env> read|write` records a run-scope consent (refused for prod writes, for `deny` and for unknown environments); `accept-changes [--note]` takes the current tree as expected and, when there were foreign changes, logs a `foreign_events` entry (`event: null` otherwise); `checkpoint-restore --paths P …` restores only the listed files (paths relative to the repository root, like `foreign_changes`; nothing left after excluding `BACKLOG.md` and the chain files → `paths-empty`, exit 2; a file equal to the snapshot is `unchanged`), and `--exec-dir D` moves `expected_tree` (every restore the executor makes itself passes it). The pipeline's own files (`BACKLOG.md` at the root; the run's own journal and its lock wherever they lie; by name in the run's plan folder, in any folder without a ledger, `*-chain.json` and its lock, specs, plans, parts, roadmaps, completion, review and report files, `*-diffs.md`, `*-followups.json`) are never foreign changes and never restored, and the chain journal is in no snapshot; none of them (except a `*-chain.json` other than the run's journal) makes the working tree dirty. `ledger-path <plan> --workdir <repo>` returns the `auto` ledger directory, whether it exists and `matched` (`plan` or `roadmap`: for a plan with a `<X>-roadmap.md` beside it the roadmap's run is found too; both runs → `ledger-ambiguous`, exit 2), read-only. `ledger-init` also stores `baseline_head` (HEAD at the first init, `""` for an unborn HEAD) and `journal` (`{path, plan}` of the chain journal, or `null`) and moves the journal's `execution` stage to `running` with the artifact `exec_dir` (relative to the journal's directory); `unit-begin` and `unit-finish` write the unit events into the journal themselves, `unit-finish` (and `ledger-init`) the artifacts `units_done`/`units_total`, `unit-begin` the end of `execution` (`done` or `failed`), and a failed journal call only adds `journal_error` to the output. `commit-run <exec_dir> --message-file F [--journal J]` commits the run's files plus the audit's `fix_files` minus pipeline artifacts and files already equal to `HEAD`, checking in this order: `no-git`, `baseline-head-unknown` (an old ledger without `baseline_head`), `index-not-empty`, `snapshots-missing` (the run's snapshots pruned and garbage-collected; only the expected tree missing → the error names `accept-changes`), `run-incomplete` (a unit still `running`, field `units`), `failed-attempt` (a `failed` unit not rolled back: commit-set files that differ from the last done snapshot and are not audit fixes, field `files`), `head-moved` (`baseline_head` is no ancestor of `HEAD`), `mixed-files` (the file had uncommitted work at `baseline_head` and the run changed it), `foreign-changes`, then an empty set → `empty: true`, then `bad-subject` (the subject must match `<type>(<scope>): …` within 72 characters, exit 2). It commits with the repository hooks (a failing hook → `commit-failed`, index reset to its previous state), returns `excluded`, `excluded_outside_chain` (left out by the artifact patterns but not chain files, or a `*-chain.json` other than the run's journal) and `incomplete` (`failed`/`pending` units, a warning), records the commit in the journal, and never uses `--no-verify`, `--amend`, `--force` or push.
- `plan-splitter/scripts/splitter_tool.py`: hand-rolled `argv` dispatch in `main`. Parts are named `<base>-a.md`, `<base>-b.md`, … (`part_id`, bijective base-26) with the roadmap at `<base>-roadmap.md`. It handles preflight, part and roadmap validation, and the verify baseline/record/status commands; `verify-record` turns plan-iterative-revision's batch JSON into the verify ledger. `gate <plan>` (and the pure `gate_verdict`) decides keep / split / borderline from `task_count`, `plan_bytes`, `modules` and `dependency_shape` of `brainstorm_tool.parse_plan_tasks` (thresholds 20 tasks / 100 KB / 40 tasks / 150 KB / 3 modules, flags to change them; exit 1 `no-tasks`); `split-write <plan> --parts <json>` checks the model's boundaries (`tasks-unassigned`, `tasks-duplicated`, `tasks-unknown`, `part-ids-not-sequential`, `unknown-dependency`, `dependency-cycle`, `group-conflict`, `dependency-order`, `missing-depends`; warnings `subtask-separated`, `lines-outside-tasks`) and only then writes the roadmap and parts from the templates, copying task texts byte for byte (`exists` without `--force`); `validate-all` requires equal task coverage and checks `task_bodies` by `sha1` (`--skip-task-bodies` after a full-cycle verification). These three exit 2 without `plan-brainstorming`.
- `plan-resolver/scripts/resolver_tool.py`: argparse. It handles bootstrap, preflight, SHA-256 `fingerprint-workspace` plus `assert-readonly <start> <current> <allowed> [<allowed> …]` (the resolver writes only its report and `BACKLOG.md`), report parsing and validation (`validate-report --root` also verifies evidence anchors against the workspace), the stuck-open gate inside `bootstrap`, `snapshot-diff`, the fix-loop commands (`discover`, `open-issues`, `protect`, `mark-fix`, `cycle-check`), and `task-census` (every plan task must be covered in the report). `validate-report --plan` lets only tasks without code files be closed by `evidence_probe`, and lists `verification: executor-reported` tasks as warnings. Incremental re-audit: `evidence-fingerprint <report> --snapshot <start> --plan <plan>` writes the report's `## Evidence fingerprint` section (the SHA-256 from the audit's start snapshot of every file named by stage anchors, issue evidence and the plan tasks' `Files` by `brainstorm_tool.parse_plan_tasks`; `excluded`/`missing`; replaced whole, before the Fix Log; exit 2 `snapshot-root-mismatch`); `rescan-scope <plan> <last-report> --snapshot <start> [--ratio 0.5]` returns `changed_files`, `missing_files`, `unverified_files`, `reaudit`, `carry`, `audit_tasks`, `titles`, `line_ranges`, `issues`, `plan_sha_changed`, `scope` (`incremental`, or `full` with `plan-changed`, `no-evidence-fingerprint` or `ratio` above `FULL_SCOPE_RATIO = 0.5`) and `reason`; `carry-forward <last-report> --scope <json> --header <json> --out <report>` writes the incremental draft (`audit_scope: incremental`, `audit_tasks`, carried lines byte for byte, `<!-- reaudit -->` stubs, issue blocks with `<!-- re-verify -->` on open ones; exit 2 `report-exists`, `inputs-inside-workspace`, `scope-mismatch`, `header-missing-fields`, `bad-input-json`, exit 1 `use-full-pass`). `validate-report` checks `audit_scope`/`audit_tasks` (missing: a warning, read as full), rejects leftover markers and malformed evidence rows and requires `audit_scope: full` for `-final`; `bootstrap --full` gives `pass_type: subsequent-full`; `cycle-check` answers `full-audit-required` for an open incremental report with everything closed, and the full pass after it never gives `stop-stalled`.
- `plan-iterative-revision/scripts/next_review_index.py`: hand-rolled dispatch. `bootstrap` starts a run and returns `settings` (plan header, else the spec at `**Spec:**`; a roadmap goes through its Source link); `record` takes the agent's issues JSON and is the single authority for loop gates (clean/converged/drain/regression/unchanged/churn/stuck/limit over the current run's history). It also computes the fingerprints (SHA-1 of category + required fix, first 8 characters), then renders, writes and strictly validates the review or completion file. `guard-begin`/`guard-check` keep diff-guard snapshots in the OS temp dir. The low-level commands (`validate-review`, `flow-analyze`, `digest`, ...) remain; `plan-splitter` calls `validate-review`. Fixtures are in `.fixtures/`. `bootstrap` also returns `journal` (the chain journal path when the file exists, else `null`), and `record` returns `journal_event`: `{stage: "revision", status, artifacts: [review=…, completion=…, verdict=…]}` with `status: "done"` and `input` (the plan path) for `clean`, `converged`, `drain` and `audit-only`, `status: "stopped"` for `limit`, `user-stop`, `regression`, `unchanged`, `churn` and `stuck`, and `null` while the loop continues; the agent passes it to `journal-event`. Incremental re-audit: `record --scope full|incremental [--tasks <ids>]` writes `**Audit scope**`/`**Audit tasks**` and the `## Task digest` table (task id + 8-hex SHA-1 by `brainstorm_tool.parse_plan_tasks`, loaded by path; no table without it, for a plan without tasks or with repeated ids); `--scope incremental` is an input error (exit 64) on the first audit of a run, without `--tasks`, with a task id the plan does not have, or with `--mode audit-only`; an incremental audit without issues gets `action: full-audit-required` (nothing written, the same audit again in full), and a skipped contract whose tasks are all unchanged is carried back with the warning `contracts-dropped`. `digest` adds `task_digest` (`available`, `plan_sha_changed`, `changed`, `new`, `removed`, `unchanged`, `focus`, `dependents`, `tasks`, `line_ranges`, `changed_ratio`, `scope`: `none-changed` | `incremental` | `full`, `reason`, `warnings`; full above `FULL_SCOPE_RATIO = 0.5`) for the plan of the latest review's `**Audited plan**`, and `validate-review` warns `task-digest-malformed`.
- `plan-writing/scripts/plan_tool.py`: argparse. `plan-path` (`<X>-spec.md` → `<X>-impl.md`) and `plan-check` (plan format contract, including the `**Environments:**` header block with quoted user permissions and per-task `**External:**` lines: `**Spec:**`/`**Tier:**` header, task headings and unique ids, task core per tier, backticked file paths, no commit steps, no placeholders; `--root` checks Modify targets). Reference plan in `tests/fixtures/`. Tasks, their bodies and code line counts come from `brainstorm_tool.parse_plan_tasks` (a task ends at the next task heading or a heading of its level or higher; without `plan-brainstorming` the local `_local_plan_tasks` with the old rules and the warning `plan-brainstorming not installed alongside`); each entry of `tasks` has `line`, the heading's line number. `plan-check` reads the chain settings through `brainstorm_tool.resolve_settings` (plan header, else the spec at `**Spec:**`) and returns `settings`, `task_count`, `plan_bytes`, `lang`, `oversized`, `size_class` (`small` ≤ 15 tasks, `large` over the budget, else `medium`; `null` without tasks) and `budget` (`tasks`, `bytes`, `source`: `brainstorm_tool`, `default` or `flags`). Above the budget (`brainstorm_tool.SIZE_BUDGET`, 40 tasks or 150000 bytes; `--max-tasks`/`--max-bytes` override it, a value that is not a positive integer is exit 2) it warns `plan-oversized: N tasks, M bytes (budget …)`, never an error. It checks `` **External:** `name` (read|write) `` against the environment's `read=`/`write=` rights and the size rule: more than 100 lines of code in a task without `**Size:** <N> lines — <reason>` warns, more than 150 fails. `plan-check` also returns `journal` (`journal_path_for(plan)` when that file exists; `null` when it does not, when `plan-brainstorming` is missing or the spec cannot be found).
- `plan-brainstorming/scripts/`: a Node visual-companion server (`server.cjs`, started with `start-server.sh`), plus `brainstorm_tool.py` (argparse). It handles `spec-check` (spec contract: 8 headings in order, empty Open Questions, Tier line; it also returns `volume`: the item counts of Components, Testing Strategy and Out of Scope, `spec_bytes`, `estimate_tasks = components × TIER_TASK_FACTOR[tier] + testing_items`, `budget_tasks` from `SIZE_BUDGET` and `over_budget`, with the warning `volume-unknown` for a Components section without items; `volume` never changes the verdict), `findings-parse` (validates a JSON findings list, assigns ids `F1..Fn`, checks file/line against `--root`) and `findings-coverage` (every finding id is mentioned in the spec). It also owns the formats other skills load: `detect-lang` (`ru` when Cyrillic letters are over 5% of all letters), `plan-tasks <plan>` (`parse_plan_tasks`, the one parser of plan tasks: per task `id`, `title`, `level`, `line_start`/`line_end` (1-based, inclusive), `checkpoint`, `section`, `files` (`{path, action, lines}` of the `**Files:**` block by `extract_files` rules), `refs` (task ids in `**Preconditions:**`), `size_bytes`, `code_lines`, `sha1` (8 hex of the body without trailing blank lines); `malformed` and `duplicates`; an unreadable file is exit 2 `plan-unreadable`), `settings` (`resolve_settings`, the single reading rule for chain settings; `spec-check` validates the `> Chain:`, `> Environment:` and `> Backlog:` lines and returns `lang`, `chain`, `environments`, `backlog`), and `backlog-append` / `backlog-parse` / `backlog-mark` / `backlog-unmark` / `backlog-sweep` for the shared `BACKLOG.md` at the repository root (append to the end of a goal's section only; every other byte must stay unchanged; items are `[ ]` open, `[x]` taken into an approved spec, `[-]` cancelled by the user, and `backlog-parse --state` filters them; `backlog-mark` checks off and `backlog-unmark` unchecks one item, changing only its checkbox byte: `marked`/`unmarked`, `already`, `cancelled`, `not-found` or `ambiguous`, the last three exit 1; `backlog-sweep` is read-only and returns a section's open items and the specs of its chain journal `<section>-chain.json`, found by exact name under the root, or `ambiguous-journal`, exit 1). A malformed settings or Tier line above `# Goal` (`> chain:`, `> Chain :`) fails `spec-check` with `malformed-metadata` and is a warning in `settings`, and a `> Backlog:` value that cannot be a file name (`\ / : * ? " < > |`) fails it with `backlog-not-a-file-name`; the user section (`My notes` / `Свои заметки`) is matched without regard to case and refused as `--section`; `backlog-append` writes through `_atomic_write_text` (keeps the file mode, writes to a symlink's target). It also owns the chain journal `<goal>-chain.json` (next to the spec; `<goal>` is the spec's `> Backlog:` value, else the spec name without `-spec.md`; next to the plan for a plan without `**Spec:**`; schema in `assets/chain-journal.schema.json`): `journal-path <file> [--create]` (roadmap or part → master plan → spec; `--create` also registers the master plan when given a plan, roadmap or part), `journal-event` (stage transitions of `writing`, `revision`, `split`, `execution`, `diffs`, `audit`, `commit`, checked: `illegal-transition` exit 1; `done → running` only with `--reason drift|audit-open|recommit|user-request`, where `audit-open` needs the stored audit `status=open` (checked before this call's artifacts are merged) and `drift` an answered or applied `drift: <stage>` question or a changed input; `--input` stores the input SHA-256 on `done`), `journal-unit`, `journal-question` (without `--answer` the stage becomes `stopped`; `--spec` binds a new plan entry, or one without a spec, to its spec, and a different spec is `journal-plan-unknown`, exit 2), `journal-answer` (`open → answered → applied`), `journal-finding` (one per `file` + `summary`, appended to `BACKLOG.md` with `--backlog-root`), `journal-commit`, `journal-export-findings` (rewrites `<goal>-followups.json`, the `findings-parse` input format), `journal-show` (per plan: stage statuses, current stage, `next_action` (`answer` while any question of the plan is open, on any stage), unit progress, open questions), `journal-reconcile [--rebuild]` (statuses from the artifacts, drift questions; `--rebuild` for a corrupt journal) and `journal-validate` (structure, ids, time fields in the `YYYY-MM-DDTHH:MM:SSZ` format, event replay; `--rebuild` ignores a bad time and leaves it to a hand fix). Writes take `<journal>.lock` (`journal-locked` after 10 s, a lock older than 60 s is taken over with a `lock-takeover` event) and an atomic replace; a corrupt journal is `journal-corrupt` (exit 2) and is never overwritten; a write the file system refuses is `journal-write-failed` (exit 1).
- `plan-chain-runner/scripts/chain_tool.py`: argparse; handlers return `(code, dict)` and `main` prints the JSON. It is the runner's deterministic scheduler and keeps the optional `runner` section of the chain journal (`version`, `profile`, `specs`, `graph`, `models` with an optional `fallback` per role, the optional `parallel`, `start_commit`, `sessions`; `journal-validate` checks its types, that graph specs are in `specs`, and that the graph has no cycle). Errors are JSON with exit 2 (bad arguments, unreadable files, `unknown-spec`, the journal errors of `brainstorm_tool.py`) or 1 (`graph-cycle`, `session-active`, `session-stale-running`, `session-taken-over`, `runner-missing`, `no-model`). `settings-load [--file F] --profile P` returns `parallel`, the model and effort of each role (`writing`, `revision`, `split`, `execution`, `audit`, `commit`) and `pinned` (per role, `true` for a full model id rather than an alias `sonnet`/`opus`/`haiku`/`fable` or null) from `~/.planforge/runner.json` (`PLANFORGE_HOME` moves the directory; a missing file or missing roles fall back to the built-in defaults of the host profiles `claude-code`, `github-copilot` and `fallback`); `settings-save` merges one profile into that file with an atomic write, only on the user's consent; `model-pick --profile P --role R [--journal J] [--unsupported M …]` returns the role's model, else its `fallback` (`fallback_used`), else `no-model`; with `--journal` the model, effort and fallback come from the journal's `runner.models` (the table the runner launched with), without it from the settings file. `run-init [--parallel N]` writes the `runner` section (every spec registered in the journal, a graph without cycles; existing `sessions` are kept; `parallel` is the confirmed width). `run-session <journal> --begin|--heartbeat|--end` keeps the active-session file `~/.planforge/sessions/<sha1 of the journal path>.json` outside the working tree (younger than 30 minutes = active: `session-active` unless `--takeover`; an older mark while a stage of the journal is `running`: `session-stale-running` unless `--takeover`; `--begin` creates the mark exclusively, so two concurrent begins cannot both succeed; `--heartbeat --id ID` and `--end … --id ID` take the id `--begin` returned and exit 1 `session-taken-over` without a write when the mark has another id or there is none; `--heartbeat` writes only that file, because the resolver fingerprints the working tree during an audit) and the `sessions` history in the journal. `run-next [--parallel N] [--in-flight PLAN:STAGE …]` returns `actions` (`run` with `skill`, `args`, `role` and the re-entry `reason`; `skip` for `split=never`, `resolver=skip` and, with `split=auto`, for a plan the splitter's `gate_verdict` keeps (`why: gate: keep (…)`); a `run` may carry `warnings` (`gate-unavailable: …`); `ask` for a machine question, with `spec` and `plan` for `journal-question --spec`; `answer` to record `rewrite` on the later `drift:` questions of a plan after an answered `rewrite`), `waiting`, `done` and `blocked`; the in-flight pairs (agents still working) are not returned but count toward the width and the one-plan rules; the width is `--parallel`, else `runner.parallel`, else the settings file, else built-in; the chain settings come from the plan header when the plan exists, else from the spec: the stages of a plan go in the order writing → revision → split → execution → diffs → audit → commit; a spec starts after the `commit` of the specs it depends on (an open audit there waits for an `open-audit:` answer); execution, diffs, audit and commit run for one plan at a time; nothing else is issued while an audit runs; a plan with an open question waits, and so do the specs that depend on it; a `stopped` stage without open questions goes back to its owner; a `failed` stage is retried once, then asked about (`stage-failed:`); a `drift:` answered `rewrite` re-issues the later `done` stages of the plan, and a `done` stage is stale only when its input file changed or a `rewrite` was answered after it (`keep` keeps it); a running audit started by an `open-audit:` answer `fix` comes back as `fix`. Machine questions start with `open-audit:`, `not-confirmed:`, `stage-failed:` or `drift:` and are answered with one token (`accept`/`fix`, `retry`/`stop`, `rewrite`/`keep`); the runner's agent also asks `model: <role>` (`retry <model>`/`retry`/`stop`) and `dirty-worktree:` (`allow-dirty`) itself. `run-eta` estimates the remaining minutes from the journal's own stage and unit timings; `run-status` summarises the plans, open questions, the waits without a question (`waits`), ETA and the session. `run-stats (<journal> | --plan <plan.md>) [--baseline <json>] [--json-out <file>]` reads only: per plan and stage the files written (by `executor_tool.py`'s `_CHAIN_FILE_RE`, loaded by path, with a fallback constant and the warning `executor-not-installed`), bytes, lines, code share, task count, the journal's minutes, model, effort and artifacts, the host's `cost_tokens`/`cost_source` fact (`basis: host`) or an estimate by a reads model derived from the artifacts (`**Audit scope**`/`**Audit tasks**` of reviews, `audit_scope`/`audit_tasks` of reports, `split_method`; `scope-unresolved` when a scope cannot be resolved), `quality`, `totals`, and with `--baseline` the deltas (absolute, per task, per KB of plan; `basis-mixed` per stage); errors `bad-arguments`, `plan-not-found`, `baseline-mismatch`, `write-failed` (exit 2). `run-status` carries the same totals as `cost`.

## Cross-skill coupling

**Cross-skill coupling.** `plan-writing` runs `../plan-brainstorming/scripts/brainstorm_tool.py spec-check` by relative path, so both skills must be installed side by side. `plan_tool.py`, `executor_tool.py`, `next_review_index.py`, `resolver_tool.py` and `splitter_tool.py` also load `../plan-brainstorming/scripts/brainstorm_tool.py` by path (`importlib`, no subprocess) for `resolve_settings` and the chain journal (`journal_path_for` gives the `journal` field of `plan-check` and `bootstrap`; `executor_tool.py` also calls `journal_create`, `journal_event`, `journal_unit`, `journal_add_commit` and `journal_load` from `ledger-init`, `unit-begin`, `unit-finish`, `commit-run` and `run-diff --include-fixes`); the splitter and resolver agents call its `settings` CLI, the executor and resolver agents call its `backlog-append`, and the agents of all six pipeline skills call its journal CLI (`journal-path`, `journal-event`, `journal-question`, `journal-answer`, `journal-finding`, `journal-export-findings`, `journal-show`), and the `plan-chain-runner` agent also calls its `spec-check` and `journal-reconcile`. Without it the settings come back empty with the warning `plan-brainstorming not installed alongside`, and the skills run without a journal. `chain_tool.py` loads it the same way, to read and write the journal (the `runner` section) and to read each spec's chain settings (`resolve_settings`), and cannot run the journal without it: `settings-save`, `run-init`, `run-session`, `run-next`, `run-eta` and `run-status` fail with exit 2 `plan-brainstorming not installed alongside`; `settings-load` and `model-pick` without `--journal` work alone (`model-pick --journal` fails the same way). `chain_tool.py` also loads `../plan-splitter/scripts/splitter_tool.py` by path for `gate_verdict` (the numeric gate of `split=auto`; missing or failing → the split stage runs with `gate-unavailable`), and the splitter's `gate`, `split-write` and `validate-all` need `brainstorm_tool.parse_plan_tasks` (exit 2 `plan-brainstorming not installed alongside` without it). The settings lines (`> Chain:`, `> Environment:`, `> Backlog:`, `**Chain:**`, `**Environments:**`, `**Backlog:**`) are parsed only there, and the task lines `**External:**` and `**Size:**` are carried into split parts verbatim. Don't rename or move that script or `references/spec-contract.md`. Output formats are also contracts between skills: splitter roadmap/part formats are parsed by `executor_tool.py parse-roadmap` and by `next_review_index.py parts` (batch mode); part ids are letters and the three parsers must agree, and plan task headings (`### Task N: <title>`) are parsed once, by `brainstorm_tool.parse_plan_tasks`, which `plan-check` always uses and the executor, the resolver's `task-census`, the splitter's count and `chain_tool.py run-stats` use for a plan with contract task headings and no malformed one (their own parsers stay for other plans and without `plan-brainstorming`); `plan_tool.py plan-check` enforces that format, and `plan-writing/tests` holds contract tests against both parsers. The chain journal (stage names, statuses, transitions, owners, artifact keys) is a contract between all six skills and `plan-chain-runner`, which schedules by it and owns its optional `runner` section; `plan-writing/tests/test_journal_contract.py` replays their event sequence for one plan against `journal-validate` and `journal-show`. `plan-chain-runner` launches the six skills by name with the arguments `run-next` returns (`/plan-writing <spec>`, `/plan-executor <plan or roadmap>`, `/plan-resolver <plan> fix|auto`, `/plan-executor <plan> commit`, …) and takes the roadmap from the `split` stage's artifacts, so a change of a skill's arguments or stage artifacts must be checked against `chain_tool.py` too. A format change in one skill must be checked against the parsers in the others.
